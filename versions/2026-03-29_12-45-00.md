## System Overview

The WebSocket module (`feat/ws` branch) adds a fourth simulation mode to Obsidian:

- **`/simulate/ws`** — interactive WebSocket lifecycle teaching page
- **`app/api/ws/route.ts`** — SSE stream that performs the TCP connect + HTTP upgrade handshake, then hands the socket to the session store
- **`app/api/ws/send/route.ts`** — POST endpoint to send a text frame from client → server
- **`app/api/ws/stream/route.ts`** — SSE stream that pushes incoming server frames to the browser
- **`app/api/ws/disconnect/route.ts`** — POST endpoint to send a close frame and destroy the session
- **`lib/ws-sessions.ts`** — global session store, frame parser, frame encoder, echo handler

**Architecture:** The browser drives a three-part protocol: (1) connect+handshake via the main SSE, (2) receive frames via the stream SSE, (3) send/disconnect via POST. The Node.js process bridges between the browser and the raw TCP socket using `net.Socket` / `tls.TLSSocket`.

## Strengths

### Correct RFC 6455 Implementation
- Proper Sec-WebSocket-Key derivation (SHA-1 + base64, with GUID)
- Client → server frames are masked with a random 4-byte key
- Server → client frames are unmasked (correct per §5.1)
- 7-bit, 16-bit, and 64-bit payload length encoding all handled
- Ping (0x09) → pong (0x0a) auto-response implemented per §5.5.3
- Close frame (0x08) with status code 1000 on disconnect

### Teaching-First Design
- Both the ping frame received and the pong frame sent are shown in the UI as control-frame dividers — learners see the full exchange without having to infer it
- Virtual mode sends a demo ping at 5s so the ping/pong exchange is always visible, even without a real server that sends pings
- Handshake request and response are shown in full with header-by-header annotation
- Sec-WebSocket-Accept derivation is shown step-by-step (key + GUID → SHA-1 → base64)

### SSRF Protection
- `isBlockedIp()` called after DNS resolution in real mode before TCP connect
- Blocks RFC 1918, loopback, link-local, and other reserved ranges

### Session Architecture
- `globalThis.__wsSessions` ensures all Next.js route bundles share one Map instance
- `socket.resume()` added after `createWsSession` attaches its data listener — fixes a Node.js v18+ regression where removing the last `data` listener leaves a `tls.TLSSocket` in paused mode

### P1 — No validation of `Sec-WebSocket-Accept` header in server response

**File:** `app/api/ws/route.ts`, line ~337–360 (real mode)

After the server responds with 101, the code checks `statusCode === 101` but does not verify the `Sec-WebSocket-Accept` value. Per RFC 6455 §4.1, the client MUST close the connection if the header is missing or the value does not equal `base64(SHA-1(key + GUID))`.

**Impact:** A misbehaving server could respond with 101 and a wrong or missing accept header; the client would silently connect. For a teaching tool, this also means learners never see the accept validation step demonstrated.

**Fix:** Parse `Sec-WebSocket-Accept` from `responseRaw`, recompute the expected value, and emit an `error` event if they do not match.

---

### P1 — RSV bits not checked

**File:** `lib/ws-sessions.ts`, `tryParseFrame()`

RFC 6455 §5.2: A client MUST fail the connection if any RSV bit (bits 1–3 of byte 0) is set and no negotiated extension defines their meaning. The current parser reads `b0 & 0x0f` (opcode) and `b0 & 0x80` (FIN) but never checks `(b0 & 0x70) !== 0`.

**Impact:** Frames from a server using undeclared extensions are silently accepted. This is also a silent lie — learners do not know RSV bits exist.

**Fix:** Add RSV check; if non-zero, emit a warning event and optionally close.

---

### P1 — IPv4 octet range not validated in `ip-guard.ts`

**File:** `lib/ip-guard.ts` (based on prior review)

The SSRF guard parses IP address octets for RFC 1918 range checks but does not validate that each octet is in 0–255. A crafted address like `999.0.0.1` could bypass checks depending on how the comparison is done.

**Fix:** Validate all four octets are in [0, 255] before range comparisons; reject malformed addresses as blocked.

## Issues

### P2 — Binary frames decoded as UTF-8

**File:** `lib/ws-sessions.ts`, `flushFrames()`, line ~217

```ts
text: f.payload.toString("utf8"),
```

Binary frames (opcode 0x02) contain arbitrary bytes; `toString("utf8")` produces replacement characters (`U+FFFD`) for invalid byte sequences. The frame is stored with `opcodeLabel: "binary"` but `text` silently loses data.

**Impact:** For a teaching tool connecting to real binary-protocol WebSocket servers (e.g., financial data feeds that use MessagePack), the displayed content is garbage.

**Fix:** For binary frames, store the payload as hex (or base64) in the `text` field and display it with a `[binary]` label in the UI.

---

### P2 — Socket not destroyed on `readHeaders()` timeout

**File:** `app/api/ws/route.ts`, `readHeaders()`, line ~49–51

When `readHeaders()` times out (10s), it resolves with `{ raw: "", leftover: Buffer.alloc(0) }`. The caller in real mode then calls `statusLine.split(" ")[1]` on an empty string, gets `undefined`, `parseInt` returns `NaN`, the `NaN !== 101` check fires, an error event is emitted, and the socket is eventually destroyed. However:

1. The 10s timeout fires while a `data` listener is still attached. After `readHeaders` resolves, the socket's data listener is removed, but if new data arrives in the window between timeout and `.off("data", onData)`, it is silently dropped.
2. The timeout path does not call `socket.destroy()` — only the caller does, and only in real mode. In virtual mode the server socket (`capturedSs`) is never cleaned up on timeout.

**Fix:** Call `socket.destroy()` inside the timeout handler, and pass the socket as a parameter to `readHeaders`.

---

### P2 — `toHexGroups()` regex silently drops odd-length hex strings

**File:** `lib/ws-sessions.ts`, line ~384

```ts
buf.toString("hex").match(/.{2}/g)?.join(" ") ?? ""
```

`Buffer.toString("hex")` always produces an even-length string, so this is safe in practice. However, the function is typed to accept `Buffer` but the `?? ""` fallback suggests the author was uncertain. The pattern is harmless but fragile — if the input type ever broadens to `string`, odd-length inputs silently lose the final nibble with no error.

**Fix:** Assert even length, or use a stricter type signature.

---

### P2 — No TTL cleanup for orphaned sessions

**File:** `lib/ws-sessions.ts`, the `store` Map

Sessions are added to `store` on connect and removed on explicit `destroyWsSession()`. If a browser tab is closed mid-session, the SSE stream's `cancel()` callback clears the `onMessage`/`onClose` callbacks but does NOT call `destroyWsSession`. The socket stays open and the session leaks.

**Impact:** In a demo environment with many visitors, this accumulates open sockets and unbounded memory growth.

**Fix:** Add a TTL (e.g., 30 minutes) cleanup timer in the session store, or destroy the session from `stream/route.ts`'s `cancel()` after a grace period.

---

### P2 — TLS certificate validation disabled with no UI warning

**File:** `app/api/ws/route.ts`, line ~301

```ts
const s = tls.connect({ socket: rawSocket, servername: hostname, rejectUnauthorized: false });
```

This is documented as an intentional educational tradeoff in `CLAUDE.md`, but the UI does not surface any warning to learners. A student who connects to a real `wss://` URL sees the TLS step succeed even if the certificate is invalid or self-signed, without knowing the check was bypassed.

**Fix:** Emit a `tls_warning` event when `isWss` is true, and show a visible callout in the UI explaining that cert validation is disabled.

---

### P2 — `onMessage` callbacks not wrapped in try-catch

**File:** `lib/ws-sessions.ts`, `flushFrames()`, line ~220

```ts
if (session.onMessage) session.onMessage(msg);
```

If `session.onMessage` throws (e.g., the SSE stream's `controller.enqueue()` on a closed stream), the exception propagates up through `flushFrames()`, which is called from a `socket.on("data", ...)` handler. An uncaught exception in a `data` handler can crash the Node.js process in some configurations.

The `emit()` in `stream/route.ts` itself has a try-catch, but `onMessage` could be any function.

**Fix:** Wrap the `session.onMessage(msg)` call in a try-catch.

## Conceptual Gaps

1. **No learner-initiated ping** — The current flow shows the server sending a ping and the client auto-responding. The reverse (client sends ping, server responds with pong) is equally important and not covered.

2. **No close handshake visualization** — RFC 6455 §7.1.2 defines a two-step close: initiator sends close frame → receiver echoes close frame → both sides close TCP. The UI shows "disconnected" but does not visualize the frame exchange.

3. **No subprotocol negotiation** — `Sec-WebSocket-Protocol` is never mentioned. Real applications use subprotocols (e.g., `graphql-ws`, `mqtt`). A note in the UI would improve mental model completeness.

4. **Frame fragmentation not taught** — Control frames cannot be fragmented; data frames can be. The `continuation` opcode is silently dropped without any explanation.
